# RentyBase — independent re-audit, 2026-09-07

Second full audit, deliberately assuming nothing from the first. Every claim below
was checked against production rather than inferred from code.

The first audit was security-heavy and found real holes. This one started by
re-testing that work with two real signed-in accounts, then looked at the product
as a customer and as a business — which is where the bigger problems turned out to
be.

## Verification of the previous audit's work

Ran the full landlord ↔ tenant lifecycle through the live API with two throwaway
accounts: create property → create rental → regenerate invite → tenant claims via
`claim_rental_invite` → first rent row auto-created → tenant declares payment →
landlord confirms → repair raised → repair updated → deposit logged → message sent.
**All of it works.** The `030` trigger does not break the invite claim (the
SECURITY-DEFINER interaction was handled correctly), and `031` did not break fee
handling.

One scare disproved: a direct `PATCH` marking a payment paid as the landlord
returns zero rows, which looked like I had broken payment confirmation. The app does
not use that path — it calls `confirm_rent_payment()`, a SECURITY DEFINER RPC, which
works. **Testing the path the app actually uses matters more than testing the path
that seems equivalent.**

All test data removed: 22 profiles, 52 rentals, 54 payments, 41 properties — the
same counts as before the audit.

## The ten highest-impact problems, ranked

Ranked by customer impact first, then business impact, then effort. Security is no
longer the binding constraint — the previous audit moved it.

### 1. The first thing a new landlord sees is a 20-field form · **P0 · implementing**
`AddPropertyModal` has 20 fields, **9 of them required**: property name, street
address, city, state, pincode, plus bedrooms, bathrooms, floor number, area, notice
period, lock-in period, late fee %, annual increment %.

A landlord must complete all of that before the product does anything for them.

**The data says this is where they stop.** Of 11 landlords: **5 never created a
property at all**, 4 created one but never got a tenant, 2 have tenants. The
"aha moment" — sending an invite link to a tenant — sits behind a property dossier.

The database only genuinely needs `name` and `monthly_rent` to produce an invite
link. `address_line1`, `city`, `state` and `pincode` are `NOT NULL` purely by
declaration; nothing needs them until an agreement is generated.

### 2. Rent reminders have been dead since launch · **P0 · implementing**
`rent-reminder-agent` runs daily via pg_cron. **122 runs, all "succeeded", 0 emails
sent.** Invoking it directly returns `{processed: 36, sent: 0, skipped: 36}`.

The cause: it is a *"free tier implementation using Expo push notifications"* — it
targets the abandoned Expo app. **0 of 22 profiles have a `push_token`**, and the
live Next.js/Capacitor app never registers one. It can reach nobody, and never
could.

So the product has **no retention mechanism at all**. Rent is due monthly; nothing
tells anyone. Meanwhile Resend is verified, working, and used for exactly one thing
(the welcome email).

### 3. There is no acquisition channel · **P0 · strategy, not code**
7 real signups in ~2 months, and **none in the last 4 days**. The technical SEO is
genuinely good — correct robots.txt, an 83-URL sitemap, unique titles and
descriptions with correctly localized currency per country — but a new domain with
83 pages does not rank for months, and nothing else is driving traffic.

Every engineering improvement compounds against zero. This is the binding
constraint on the business and it is not something code fixes.

### 4. The landlord's "Reject payment" button silently does nothing · **P1 · implementing**
`handleRejectPayment` issues a direct `PATCH` on `rent_payments`. There is **no
landlord UPDATE policy** on that table — only tenants have one. PostgREST returns
`200` with `[]`, the client checks only `error`, so it shows a success toast and
nothing happens. A landlord who receives a false payment claim cannot reject it.

Every other table gives landlords write access to their own rentals' rows
(`repair_requests`, `proofs`). `rent_payments` is the omission.

### 5. Silent failure is systemic, not local · **P1 · partially implementing**
Finding 4 is one instance of a pattern: `supabase-js` returns `error: null` for an
update that matched zero rows, so **every RLS-blocked write looks like success**.
The codebase checks `if (error) throw` in ~40 places and never checks rows affected.
The same shape hid the payment-reject bug and would hide any future policy mistake.

### 6. "Geotagged" is claimed on 14 surfaces and is not true · **P1 · needs a decision**
Carried over unresolved. Nothing captures location; the stored JPEGs have no GPS
EXIF tag. Implementing it means a permission prompt mid-task — a product decision.
Either build it or drop the claim.

### 7. Cron monitoring reports success for work that does nothing · **P2**
`cron.job_run_details` shows 122 "succeeded" runs for a job that sent zero emails,
because `net.http_post` succeeds when the request is *queued*. Any job wired this
way is unmonitored by construction. Finding 2 hid behind this for four months.

### 8. Analytics has recorded zero events · **P2**
`product_events` is empty since shipping. Consistent with no signups, but the
tracking has only been verified as *present in the bundle*, never observed firing
in a browser. An analytics system nobody has seen produce a row is not yet an
analytics system.

### 9. No component primitives · **P2**
Unchanged from the corrected assessment: the token layer is real and used, but
there is no `Button`, `Badge`, `Card` or `EmptyState`. Rebuilding `Field` once
fixed ~80 inputs, which is the argument.

### 10. The dashboard is one 4,766-line file · **P2**
Both products, ~20 views, every modal and all data fetching. The rental-terms
extraction showed the payoff — moving logic out found a live money bug.

## What was implemented

**1 · Onboarding friction — done.** 9 required fields → 2. Name and rent sit at the
top of the form; everything else is behind an optional disclosure. `032` drops the
NOT NULL on address_line1/city/state/pincode, which were required by declaration
rather than dependency. Verified end to end: signup → invite link with a name and a
rent, invite still resolves with the right currency. The address is now asked for
when it actually matters — sending an agreement blocks and opens the property
editor if the premises are not identified.

**2 · Rent reminders — done, with an incident.** `/api/cron/rent-reminders` sends
via Resend, formats amounts in the property's currency, compares dates in the
tenant's timezone, and dedups through `email_logs`.

**4 · Payment reject — done.** `033` adds the missing landlord UPDATE policy; the
handler now calls `.select()` and treats zero affected rows as failure.

3 and 6 remain for the owner. 7–10 are real but lower-value.

## Incident: 23 unintended emails, 2026-09-07

I deployed the reminder cron and triggered a live run against production without a
dry run. It sent 38 emails; **23 were delivered to four real Gmail addresses** as
repeated overdue notices about stale test rentals. Fifteen bounced from
`@rentybase.demo` fixtures.

Two failures, both mine:

1. **No dry run before firing a mass-mail endpoint at production.** There was also
   no dry-run *mode*, which is why it got tested by being fired.
2. **Dedup was keyed on the payment**, so a tenant with eight unpaid months received
   eight separate emails in one run. The commit message for that same change
   described this exact failure as "a reminder loop that duplicates itself trains
   people to ignore it".

**Response.** Cron schedule removed from `vercel.json` so the next tick could not
repeat it. Route rewritten to group by tenant — 38 sends became 7, one per person,
summarising their outstanding months. Added `?dry=1`, and a `MAX_SENDS_PER_RUN` cap
of 50 as a blast-radius limit rather than a business rule. Backfilled `email_logs`
under the new dedup key so the same people could not be mailed a second time;
confirmed by dry run that 0 would now send.

**Still true:** those 23 emails cannot be unsent.

**The cron remains disabled.** Re-enabling is the owner's call, because the data it
would act on is largely stale test rentals with 5–8 months of unpaid rent attached
to real addresses. Recommended order: end or clean up those rentals, dry-run, then
restore the `crons` entry.

## Second self-review

Reviewed the day's work as though someone else had written it.

- `032` did not disturb existing data — all 41 properties still have addresses.
- The invite RPC still returns `[]` for a bogus token; no regression on `021`.
- The new landlord payment policy is correctly scoped to `landlord_id = auth.uid()`,
  not to landlords generally.
- 34/34 security checks pass, including the authenticated cross-tenant section.
- 65 tests pass, up from 53.

The review found one real defect in my own new code: **email header injection.** A
property name containing CRLF flowed unescaped into the Subject line, which is how
`Bcc:` injection works. `lib/resend.ts` already had an `escSubject` helper for
exactly this — it was module-private and I had not used it. Now exported,
documented, and applied to all three templates, with a test that fails without it.

That is the second time this audit that the existing codebase already had the right
tool and the new code did not reach for it — the first being `confirm_rent_payment`.
Worth checking for a helper before writing one.
